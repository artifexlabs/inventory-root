# DO23_7_5 — the 0.2.0 break train, the release-train tooling, and the parity TCK

*Staged 2026-08-22 from the ranked to-do assessment. The numbers in the filename
are that ranking's item numbers: **2** = `correlationId` on the bus envelope,
**3** = ongoing item 6 (data items as first-class media), **7** = release-train
tooling, **5** = Phase 20 step 0 (parity TCK extraction). Execution order is
owner-chosen: **2+3 together, then 7, then 5.** Like UPC_CODE.md and
MAVEN_RELEASES.md before it, this doc is a staging area: when the work executes
it migrates into PLAN.md as phase entries and this file retires.*

## Why this order

- **2+3 ride one API break.** Both change `inventory-api`
  (`BusEnvelope` gains a request id; the data-item model gains contracts), and
  Phase 19's recorded chore means every api change costs the same
  api → impl-root → bom → apps release ceremony whether it carries one change
  or five. One 0.2.0 train, not two.
- **The break window is closing.** `0.1.0` is public on Central and real labels
  are printed onto real objects. Pre-1.0 breaks are sanctioned (owner rule),
  but the Phase 15 lesson stands: model changes are cheap exactly once, and
  that window is now.
- **7 lands between the code and the ceremony.** The 2+3 work merges to
  develop as SNAPSHOTs; nothing releases until the train runs. Building the
  train tooling *then* means its first real run IS the 0.2.0 release — the
  tooling is verified by the ceremony it exists to serve.
- **5 comes last so it sweeps everything.** The TCK extraction
  (Phase 20 step 0) refactors the twin memory/Pg suites into one
  backend-parameterized kit. Running it after 2+3 means the new data-item
  tests get swept into the kit in the same pass instead of being written into
  a structure that is about to be replaced. Item 2+3 tests should be written
  with that extraction in mind (behavioral assertions separated from backend
  fixtures).

House rules apply throughout: `mvn formatter:format` after Java edits,
`mvn tidy:pom` after pom edits, clean verify before pushing interface changes,
no pushes without explicit say-so, and no physical printing (nothing here needs
hardware).

## Part 1 — `correlationId`: status events become attributable (ranked item 2)

**Closes the Phase 21 known gap**: "`correlationId` is unpopulated
(`BusEnvelope` has no request id yet), so printer events are unattributed and
route to admins." After this, a user who sends a print job sees its outcome —
today only admins do.

### Design

1. **`BusEnvelope` gains `String requestId()`** (api, `bus` package) — a ULID
   minted once per external request, threaded through everything that request
   causes. This is the BREAKING change: `BusEnvelope` is an interface and the
   only in-tree implementor is `DefaultBusEnvelope`. Decision (proposed):
   make it a required accessor, not a `default null` — a nullable request id
   reproduces the current gap with extra steps. The wire format gains a
   `requestId` key beside `token`/`userId`/`principal`; envelopes are never
   persisted, so there is no stored-data compatibility concern.
2. **Minted at the gateway.** `BusClient` (inventory-web-api) stamps a fresh
   `Ulid` per HTTP request when it builds the envelope. `forward(...)` in the
   public verticles already passes envelopes verbatim, so the id reaches the
   `storage` address and every orchestrator for free.
3. **Carried into printer packets.** `PrintPackets` gains `actor` and
   `correlationId` fields (api, beside the existing packet fields), populated
   by `LabelsVerticle` from the envelope when it packs. Packets are
   self-contained by design; attribution is part of the packet's payload, not
   ambient state.
4. **Populated on publication.** Every `StatusPublisher` call site that has an
   envelope or packet in hand fills `StatusEvent.correlationId` AND
   `StatusEvent.actor` (the field already exists on `StatusEvent` — it has
   simply never been fed for printer outcomes): the Brother/Zebra refusal
   paths via the packet, `BusGuard` denials via the envelope,
   `LabelPrinterVerticle` outcomes via the packet.
5. **SSE scoping does the rest, unchanged.** `StatusStreamBroadcaster`
   already filters by `actor`; once printer events carry one, they route to
   the requesting user (admins still see everything unattributed). No gateway
   changes beyond tests.

### Files touched

- api: `BusEnvelope`, `PrintPackets` (+ package-info wording).
- impl-bus: `DefaultBusEnvelope`, `Envelopes`, `BusGuard`,
  `ServiceVerticle`, `StorageVerticle` (pass-through only), `LabelsVerticle`.
- printer-common: `LabelPrinterVerticle`; brother/zebra refusal-path
  publish sites.
- web-api: `BusClient` (minting), `StatusStreamBroadcasterTest` additions.

### Tests / gates

- Envelope JSON round-trip carries `requestId`; the immutability/deep-copy
  test extends to it.
- A packet built from an envelope carries the envelope's actor + request id.
- Broadcaster test: a printer StatusEvent with `actor=alice` reaches alice's
  stream and NOT bob's; an unattributed system fault still reaches admins
  only (the existing 8 scoping tests grow by these cases).
- End-to-end (JVM, fake printer): request a print as a non-admin user with a
  deliberately failing format → the SSE stream for THAT user delivers the
  refusal with matching `correlationId`.
- `StorageIsolationTest` untouched and green (the change adds no backend
  access anywhere public).

## Part 2 — Data items: manifests for media (ranked item 3, ongoing item 6)

**The last unstarted core README requirement**: physical objects AND data. A
CD, backup disk, or network share is an item whose *contents* are files —
thousands of them — described by hashes and relative paths, "rendered very
differently than physical items."

### Model decision (proposed; owner confirms at execution)

**Files are NOT items** *(one exception: archives — below)*. A data medium's
contents become a **manifest**: rows of `(relativePath, sizeBytes,
hashAlgorithm, hash, mimeType, modifiedAt?)` attached to the medium item.
Making each file an `Item` would explode the containment tree and the audit
log for zero benefit — files have no par values, no labels, no containment of
their own. The medium itself stays an ordinary
physical/remote item (`MediaKind.PHYSICAL_MEDIA` / `REMOTE_STORAGE` — the
enum already exists), so "the physical object that contains the data" is
called out exactly as item 6 asks.

The payoff feature is **lookup by hash**: "which disc has this file?" and
"is this file already archived anywhere?" — the inventory question, asked of
data.

**Archives are containers too — the one exception to "files are not items."**
An archive file (zip, tar, tgz/tar.gz, iso, …) on a medium is BOTH things at
once: an ordinary entry in its medium's manifest (one file with its own hash,
size, and mime type) AND an item in its own right, decomposed recursively the
way a medium is. The model already has the seam: `DataInfo.archive` has
existed since Phase 1 ("archives as sub-containers") — an archive becomes an
item with `archive = true`, contained by the medium item through ordinary
containment, carrying its OWN manifest of contents. Archives inside archives
decompose the same way, to any depth. Because the server never possesses the
bytes (ingestion is client-computed manifests), decomposition happens at
ingestion: the ingesting client reads into the archives it finds, and the
payload expresses the nesting — the server mints the archive items and
attaches each scope's manifest. *(Execution-time decision: nested entries in
one payload vs one call per archive scope; either way the medium's whole
ingest should land as one unit of work.)*

**Manifest storage is normalized — entry rows stay tiny, text lives once.**
A full relative path (or any repeated string) per entry row is too much data
to keep around at media scale. The entry table stores small integers; the
text lives in lookup tables:

- **`hashAlgorithm`** → a tiny integer enum, defaulting to `sha256`.
- **`mimeType`** → a small integer lookup table (`mime_types(id, name)`) —
  never the full text of a mime type on a record.
- **Every path component** (each directory or file name) → a row in a
  `path_elements(id, name)` lookup table; an entry's path is stored as the
  SEQUENCE of component ids. Components are append-only: a **rename** (a
  command the system must offer) looks up or creates the components of the
  new name and rewrites the entry's id sequence — existing components are
  NEVER overwritten or reused, because other entries still reference them;
  overwriting would destroy existing integrity.

Worked example — a `path_elements` table:

| id | element |
|---|---|
| 1 | `.git` |
| 2 | `home` |
| 3 | `mykel` |
| 4 | `README.md` |
| 5 | `git` |
| 6 | `somerepo` |
| 7 | `config` |

`/home/mykel` is stored as `[2, 3]`; a `git` directory in that home dir is
`[2, 3, 5]`; the config file of a repo `somerepo` inside it is
`[2, 3, 5, 6, 1, 7]`.

Path queries translate names to ids FIRST, then match id sequences: searching
for the subpath `mykel/git` means finding `[3, 5]` as a contiguous
subsequence in stored paths; searching for `jerry/git` fails immediately at
translation — no `jerry` component exists — without touching an entry row (a
free negative).

*Open, measured at execution rather than guessed:* the element table's growth
and the right physical layout for sequence matching — Postgres `int[]` with a
GIN index (element-containment prefilter, order verified afterward) vs a join
table vs a denormalized text column kept beside the ids for substring search.
The gate below ingests a real, large directory tree so this gets decided from
a scan of real data, not intuition.

### API (inventory-api — the second half of the 0.2.0 break)

- **`DataEntry`** record: `path` (relative, normalized `/`-separated),
  `sizeBytes`, `hashAlgorithm` (lowercase, e.g. `sha256`), `hash` (lowercase
  hex), optional `mimeType`, optional `modifiedAt`. The API speaks readable
  STRINGS; the integer dictionaries are a storage-side concern only — no
  lookup-table id ever crosses the contract.
- **`DataInfo` gains optional `locator`** (mount URI / volume label /
  share path — free text). Record constructor change = breaking; rides the
  train.
- **`DataSystem`** interface (new, beside `RegionSystem`):
  `replaceManifest(itemId, List<DataEntry>)` (whole replacement — a manifest
  is a snapshot of a medium, not a row-edit surface),
  `renamePath(itemId, fromPath, toPath)` (the ONE targeted edit the owner
  requires — a metadata correction that must not force re-hashing a medium),
  `entriesOf(itemId, query?, page, size)`,
  `findByHash(algorithm, hash)` → the items whose manifests contain it.
  Refuses `replaceManifest` on an item whose `DataInfo.kind` is `OBJECT`.
- Audit vocabulary: `data.replace` (details: entry count, total bytes —
  never the entries themselves; `audit_events` is the replay feed every
  consumer pages, the Phase 15 asset-archival lesson) and `data.rename`
  (from/to paths).

### Storage (impl train)

- Changeset `006-data.yaml`, the normalized shape: `path_elements(id,
  name)` (unique on name, append-only), `mime_types(id, name)`, and
  `data_entries(item_id fk cascade, path_ids, size_bytes, hash_alg
  smallint, hash, mime_id, modified_at)` — uniqueness on `(item_id, path)`,
  index on `(hash_alg, hash)`, plus whatever index the path-layout
  measurement (above) picks for subsequence search. Additive — no
  schema-collapse license needed.
- `PgDataSystem` (replace = one transaction: delete + bulk insert +
  dictionary upserts + audit row; rename = lookup-or-create components +
  rewrite the sequence, one transaction) and `InMemoryDataSystem` twin —
  the twin stores plain strings; dictionary encoding is a Pg storage
  choice, not a behavior, so the TCK never sees it. Written TCK-shaped
  (assertions in methods that take the backend as a fixture) so Part 4
  sweeps them cheaply.
- Bus: `data.replace-manifest` (WRITE), `data.rename-path` (WRITE),
  `data.entries` (READ), `data.by-hash` (READ) in `BusActions`; a
  `DataStorage` registrar behind `StorageVerticle`; the public verticle is
  a pure `forward(...)`.
  Replace-manifest is one storage message — whole unit of work, per the
  storage rule (large manifests ride one envelope; if a manifest ever
  exceeds envelope comfort, the recorded escape is chunked staging on the
  storage side, decided then).

### Gateway + web

- `PUT /api/v1/items/{id}/data/manifest` — accepts a JSON array of entries
  **or** `text/plain` `sha256sum`-format lines (`<hash>  <path>`), so
  `find . -type f -exec sha256sum {} + | curl --data-binary @-` is the whole
  CLI ingestion story. No custom client tool needed. (The plain-text form
  carries path + hash only — sizes, mime types, and archive decomposition
  come via the JSON form; a helper script that emits it can come later
  without any server change.)
- `GET /api/v1/items/{id}/data/entries?query=&page=&size=`,
  `GET /api/v1/data/by-hash/{alg}/{hash}`.
- Web app: on items whose `DataInfo.kind` ≠ `OBJECT`, the detail page swaps
  the containment children panel for a **manifest panel** — entry count +
  total bytes rollup, a path/hash search box, paged file table — and a
  replace-manifest upload control. That IS the "rendered very differently"
  requirement; visual polish beyond structure waits for Phase 18.
- iOS: deferred, contracts-settle-first (the Phase 15/16 pattern).

### Tests / gates

- Twin memory/Pg suites: replace-then-replace leaves no orphans (delete+insert
  transactional), by-hash finds across media, kind refusal, `sha256sum`
  parsing (web-api), path normalization, rename rewrites the path without
  touching hashes and never reuses a component id, subpath query matches
  `[3, 5]`-style contiguous sequences and unknown components fail fast,
  archive decomposition yields the archive as BOTH a parent-manifest entry
  and a contained `archive=true` item with its own manifest. Audit rows
  carry counts, not entries. Full `just verify` green; iOS untouched and
  still green.
- Manual gate: hash a real, LARGE directory tree (the path-layout
  measurement), ingest via curl, find one file by hash in the web UI, and
  rename a directory seeing every descendant path follow.

## Part 3 — Release-train tooling (ranked item 7)

**Automates Phase 19's recorded chore**: release api → bump impl-root's pin →
release impl train → re-pin + release bom → bump the apps. Runs LOCALLY only
(owner decision: CI verifies, never releases). The tooling's first real run is
the 0.2.0 train that ships Parts 1+2.

### Shape: guided steps, not one shot

`autoPublish=false` means a human publishes each staged bundle in the Central
portal between steps — the tooling therefore CANNOT be a single command, and
should not pretend to be. New `[group('release-train')]` Justfile recipes:

- **`train-plan`** — read-only: current released pins vs local SNAPSHOT
  versions across api / impl-root / bom / apps, what a train run would do,
  and preflight checks (clean trees, `MAVEN_GPG_PASSPHRASE` set, on the
  right branches).
- **`train-api version`** — guards (clean tree, branch, passphrase env),
  then `release:prepare`/`release:perform` in inventory-api, then prints the
  ONE manual step: publish the staged bundle in the portal.
- **`train-impl api_version version`** — sets `inventory.api.version` in
  impl-root's pom (`versions:set-property`), `tidy:pom`, commits the bump,
  clean verify, releases the train, portal reminder. (Local `~/.m2` installs
  from `release:perform` let each step proceed without waiting on Central
  sync — the portal publishes remain the durable record.)
- **`train-bom api_version impl_version version`** — re-pins both properties
  in inventory-bom, tidy, commit, release, portal reminder.
- **`train-apps bom_version`** — bumps the BOM import in the four apps,
  `tidy:pom` each, full `just verify` (clean — the IDE-poisoning rule),
  commits per repo, then prints what to push. **Nothing pushes** — house
  rule, and the recipe says so like `release` already does.

### Guards (each step)

Clean tree in the target repo; correct repo/branch; tag not already taken;
refuses if `MAVEN_GPG_PASSPHRASE` is unset (the recorded pinentry fix — the
600 s agent cache WILL expire mid-train); refuses SNAPSHOT pins in anything
about to release (the Central dM-rejection lesson).

### Gates

`train-plan` output verified against the known 0.1.x state; a `-DdryRun`
pass of `train-api`; then the real proof is the 0.2.0 train itself. RUNBOOK
gains a "library release train" section pointing at the recipes; the
Phase 19 chore paragraph in PLAN.md gets a pointer on migration.

## Part 4 — Parity TCK extraction (ranked item 5, Phase 20 step 0)

**No API change.** Refactors the hand-written memory/Pg twin suites into one
backend-parameterized behavior kit, so a behavior is written ONCE and every
backend proves it in the same reactor pass. Phase 20 records this "pays for
itself even if no second backend ever ships."

### Placement decision (proposed)

**In core's attached tests-jar** — the `GpsJpeg` pattern already in place
(`inventory-impl-pg` consumes core's test-jar today, see its pom's
`<type>test-jar</type>` dependency). No new module, no new release-train
member. The `inventory-impl-tck` module alternative stays recorded in
Phase 20 as the escape hatch if a backend ever lives OUTSIDE the impl-root
train and needs the kit as a main-scope artifact.

### Shape

Abstract JUnit classes in `inventory-impl` `src/test`, one per contract
surface, each declaring fixture hooks (`protected abstract` backend factory +
per-test reset) and carrying ONLY behavioral assertions:

- `InventorySystemTck` — CRUD, single-parent containment + re-parent +
  cycle refusal, coordinate inheritance (three-deep), tags (existence /
  glob / regex), identities (idempotent claim, cross-item refusal, 409
  precedence), refusal ordering.
- `AssetStoreTck` — assets, regions/dots, replace-with-archival recovery,
  from-photo / from-upc transactionality (refused claim leaves no orphan).
- `AuthTck` — users, tokens, federated identities, revocation.
- `AuditTck` — same-transaction commit, `seq` strictly-increasing paging
  under concurrent writers, exactly-once, `truncatedTo(MICROS)` timestamp
  precision (the Instant-vs-timestamptz lesson).
- `DataSystemTck` — Part 2's suite, swept in (it was written TCK-shaped).

Memory harnesses live in core and REPLACE the bodies of
`InMemoryInventorySystemTest` / `Phase3StoresTest` / `AuthServicesTest` /
`UpcCreationTest`; the Pg harnesses in `inventory-impl-pg` extend the same
classes over the existing Testcontainers lifecycle, replacing the
behavioral bulk of `PgInventorySystemTest`. Backend-SPECIFIC residue stays
put by design: Pg SQL details (recursive CTE, `ON CONFLICT`), EXIF parsing,
catalog adapters — those are not parity behaviors.

### Migration discipline / gates

Inventory every existing test method first; each maps to exactly one TCK
method or is recorded as backend-specific residue — **no assertion is
silently dropped** (per-suite method counts may only grow). Full impl-root
verify green with both harnesses running the full kit; a deliberate
one-line behavioral break in the memory backend must fail BOTH its harness
and nothing else (proving the kit actually runs against both). Format pass,
then done.
